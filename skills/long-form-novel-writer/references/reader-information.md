# 讀者資訊管理

## 分層
- **已知**：文本已公平呈現，普通讀者應能記住。
- **可推論**：線索足夠，但文本尚未確認。
- **誤信**：文本刻意導向的暫時理解；必須有公平依據，不能靠隱藏 POV 已知事實作弊。
- **保留**：文本尚未提供足以確定的答案。

## 每場最低紀錄
在 scene card 標出新增／確認／誤導／反轉／保留；章後彙整至 `reader-ledger.md`。讀者帳本不能從角色知識矩陣推導取代：角色知情而讀者不知、讀者知情而 POV 不知都很常見。

## 檢查
1. 重提資訊要改變功能、情境或解釋，否則標重複風險。
2. 反轉必須能回指先前種子；若只能事後解釋，列為 P1 公平性問題。
3. 每個 Active 問題記最晚回應章範圍；延期需寫原因。
4. 章末選擇最強未解問題，不強制做懸崖。

## 自造名詞首次出場（可選、非阻斷）

需要釐清讀者困惑時，沿用帳本的資訊 ID，記錄詞語在讀者目前可見文本中的首次出場；不另建必填詞典，也不按新詞數量、固定字數或題材套用門檻。先查已提供前文與別名：本章首次出現不等於全書首次介紹，未載入的前文不能當成「從未交代」。

分開看兩件事：
- **可追蹤的眼前資訊**：它大致屬於什麼，或它讓角色此刻能做／不能做什麼。動作、結果、對話與情境都可承載，不必插入百科定義，也不必兩項皆明說
- **刻意保留的真相**：來源、機制、代價或身份可以仍是謎。讓讀者追得上眼前選擇，不等於提前揭密

在帳本的可選小節註記已知／可推論／誤信／保留；作者意圖沒有來源時寫 `unknown`，不可替作者編造理由。若無法確認首次出場或缺少可引用上下文，只列問題與缺口。建議先補最小的動作／效果線索，必要時保持原文；不是要求每章新增 Owner 核准、改變正典或自動擋稿。

### 原創合成例子（人工討論用，不是語義測試 oracle）

- **可追蹤、仍保留謎底**：「她把霧扣夾上門縫。追兵推門時，門後只響起她三分鐘前的腳步。」讀者可推論霧扣會干擾追蹤；它如何做到仍保留，不必解釋完整機制
- **可提出疑問的缺口**：「霧扣過了逆衡，於是他選了第三條路。」如果這就是全部可用上下文，類別、效果與選路依據都不明；詢問是否需要一個可見後果，不能宣判全書漏講，也不能把兩個詞計成兩次失敗
- **刻意超現實的反例**：「霧扣在星期四開花，所有門都忘了自己通往哪裡。」若已有可引用的敘事約定支持陌生化，可保留意象，不強迫補器物定義；約定未提供則意圖是 `unknown`
- **不可靠敘事的反例**：「我敢說霧扣只是裝飾。可每次我碰它，鐘都少走一格。」前句是敘述者的說法，後句提供可觀察反差；不要把前句升格為世界真相，或要求作者立即揭穿敘述者
- **已介紹別名的反例**：前文「守門人把那枚能重播腳步的銅夾叫作霧扣」；本章「她扣上回聲夾，那正是守門人給的霧扣」。有前文與本章可定位證據時，沿用同一資訊 ID；只看到本章時，不假定前文已交代或未交代

審稿輸出沿用 [reviewer-protocol.md](reviewer-protocol.md) 的 v2 契約：`reader` issue 需兩段不同、可定位的原文；只有一段或缺證據就放 `questions`，不要捏造第二段來證明「缺少解釋」。來源 hash 由既有流程保存及重查，不能以手填 hash 假裝已驗證。引用錨定只驗證引文位置與來源版本，不證明讀者感受、作者意圖或文學品質。
